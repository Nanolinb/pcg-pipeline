# 发布验证与用户验收规范

## 原则

每个功能版本在发布前后都必须先由开发侧完成验证，再交给用户。不能只用“代码已提交”或“脚本可导入”代替功能验收，也不能把明显可自动化的流程全部留给用户。

## 发布流程

1. **冻结验收对象**：记录发布标签、提交哈希、Godot 版本、平台和参考硬件。
2. **运行自动门禁**：执行 `tools/run_gate.sh`，保存完整日志；失败必须修复并发布补丁，不得删除失败测试。
3. **执行真实功能流程**：按用户场景调用实际窗口、资源、生成和保存功能，不只检查类是否存在。
4. **执行图形验证**：可见工具必须在非 headless 模式运行并保存真实截图；鼠标无法可靠自动化时使用实际控件驱动和视口截图，但要说明方式。
5. **检查保存与恢复**：保存、关闭/重载、继续编辑；需要原子保存的资产必须覆盖中断恢复。
6. **检查回归与已知问题**：区分既有引擎警告、新增错误和未覆盖项。
7. **形成发布报告**：给出结果、证据路径、用户使用方式、验收清单和反馈渠道。
8. **同步版本记录**：更新 requirements/changelog/release 文档，并上传腾讯文档空间。

## 报告内容

每版报告必须包含：

- 版本、标签、提交、日期和验收环境。
- 实际执行的命令与结果，不只列测试总数。
- 关键用户场景和截图证据。
- 已知限制、未验证项和失败处理。
- 用户可逐步操作的验收清单。
- 回滚基线和问题定位方式。

## 失败处理

- 发布后发现功能缺陷，先保存原始日志和复现步骤，再建立修复提交。
- 修复需要提高修订版本并重新跑完整验收，不覆盖旧证据。
- 不移动已发布标签来隐藏历史；文档回填可以追加独立提交。

## 建筑样本纵向闭环验收（v0.20 起）

除了单资产测试，必须使用 `G3A_SlotLoop` 做端到端验收，并逐条记录 `slot_id → L0 task → CandidateEnvelope → published asset + version → SlotBinding`：

1. 从已确认概念稿/风格包创建含多种组件占位的建筑功能白盒。
2. 批量提取并按组件族/兼容规格归并需求，优先匹配已有库资产和任务。
3. 批量生成缺失/不合格需求的 L0 任务，按风格分发给人工、Tripo/Meshy 或程序生成器。
4. 所有候选进入同一收件箱和 L1 验收发布，不允许绕过标准化。
5. 按槽位批量绑定正式资产并替换占位显示，保留功能白盒、接口、碰撞和占用数据。
6. 保存 BuildingRecipe，重开并局部重建，检查槽位、资产 ID、版本、变换和人工覆盖不变。
7. 注入候选失败，确认白盒、旧绑定、其他槽位和发布目录零副作用。

报告必须同时给出批量归并数量、库复用数量、新任务数量、候选失败结果和绑定追踪链，不能只展示最终模型截图。
